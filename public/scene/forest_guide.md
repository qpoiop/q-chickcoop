# 맵 통합 개발 가이드

Three.js 탑다운 파밍·탈출 게임용. **맵을 여러 개 갈아 끼우는 구조**를 전제로, 맵이 바뀌어도 게임 로직을 손대지 않는 것을 목표로 한다.

---

## 1. 원칙

> **맵마다 다른 것은 설정으로 빼고, 로직은 맵을 모르게 한다.**

맵 파일은 "보이는 껍데기 + 위치 정보"일 뿐이다. 충돌·아이템·포탈 같은 동작은 전부 코드 쪽에 있고, 맵은 좌표만 제공한다. 이 경계를 지키면 맵 추가가 설정 항목 하나 늘리는 일이 된다.

---

## 2. 공통 로더 파이프라인

어떤 맵이든 아래 순서를 그대로 통과시킨다.

| 단계 | 내용                        | 맵별 차이 |
| ---- | --------------------------- | --------- |
| 1    | GLTFLoader로 로드           | 없음      |
| 2    | **껍데기 벗기기**           | 없음      |
| 3    | **크기 정규화 + 중심 정렬** | 배율만    |
| 4    | 알파 컷아웃 보정            | 유무만    |
| 5    | 충돌 생성                   | 방식 선택 |
| 6    | 앵커 수집 → 게임 요소 배치  | 설정 참조 |
| 7    | 애니메이션 믹서 연결        | 있는 맵만 |

### 2-1. 껍데기 벗기기

Sketchfab을 거친 파일은 예외 없이 아래 구조를 갖는다.

```
Sketchfab_model → <해시>.fbx → RootNode → 실제 내용
```

`RootNode`에 축 변환 회전이 걸려 있어 Y-up으로 이미 통일된다. **함수 하나로 모든 Sketchfab 맵에 대응된다.** 다른 경로로 받은 파일은 이 구조가 없을 수 있으므로, 없으면 그냥 통과시키도록 예외 처리한다.

### 2-2. 크기 정규화 — 가장 중요

맵마다 원본 스케일이 제각각이다. 실측한 예만 봐도 **73 ~ 14,302까지 200배 가까이 벌어진다.**

정규화하지 않으면 맵마다 이동속도·중력·카메라 높이·사거리·투사체 속도를 전부 다시 잡아야 한다.

**방법**: 로드 직후 바운딩 박스를 재고, 긴 변 기준으로 목표 크기(예: 120)에 맞춰 스케일한 뒤 원점 중심으로 이동.

```
scale = targetSize / max(width, depth)
```

이 한 단계로 게임 로직 전부가 모든 맵에서 동일하게 동작한다.

> **좌표는 반드시 정규화 이후 기준으로 저장할 것.** 원본 좌표를 섞어 쓰면 맵 교체 때 전부 깨진다.

### 2-3. 충돌 생성 방침

| 대상                        | 방식             | 이유                                          |
| --------------------------- | ---------------- | --------------------------------------------- |
| 지형·바위·나무 등 굴곡진 것 | 메시 그대로 충돌 | 모델 모양과 자동으로 100% 일치. 수작업 불필요 |
| 건물·벽 등 단순한 것        | 보이지 않는 박스 | 가볍고 정밀 제어 가능                         |
| 통짜로 합쳐진 맵            | 전체 메시 충돌   | 부위 구분은 포기, 대신 준비 0분               |

"막는다"는 **표면을 뚫고 지나가지 못한다**는 뜻이다. 바닥을 막으면 그 위를 걸어다니게 되고, 안 막으면 아래로 떨어진다.

## 3. 맵 설정 스키마

맵마다 아래 항목만 채우면 된다.

```
{
  url,
  targetSize,          // 정규화 목표 (전 맵 동일값 권장)
  hasAnimation,        // 애니메이션 믹서 필요 여부
  lighting,            // 조명 프리셋
  alphaTest,           // 컷아웃 필요 여부
  anchors: {           // 4장 참조
    spawn, portal, exit, lootRoom, lootBox, cover, light
  },
  manualPoints         // 앵커로 못 잡은 것들의 수동 좌표
}
```

### 확인해둘 맵 속성

| 속성            | 확인 방법                    | 영향                                        |
| --------------- | ---------------------------- | ------------------------------------------- |
| unlit 여부      | 재질에 `KHR_materials_unlit` | unlit이면 조명 세팅 불필요, 성능 유리       |
| 알파 컷아웃     | 재질 `alphaMode` ≠ OPAQUE    | 투명 처리 안 하면 잎사귀가 네모로 보임      |
| 텍스처 유무     | `images` 개수                | 0장이면 단색 로우폴리. 조명 각도에 민감     |
| 애니메이션·뼈대 | `animations`, `skins`        | 있으면 믹서 필요. 뼈대는 무기 장착에도 활용 |
| 불필요 UV2      | `TEXCOORD_1`                 | 있으면 제거 대상 (용량 낭비)                |

## 4. 앵커 매칭

맵에 이미 배치된 오브젝트를 **좌표 앵커**로 삼아 그 위에 게임 요소를 얹는다. 배치 위치를 새로 고민할 필요가 없고, 원작자가 잡아둔 구도를 그대로 쓸 수 있다.

### 4-1. 앵커를 찾는 4가지 방법

| 방법              | 조건                                                 | 작업량     |
| ----------------- | ---------------------------------------------------- | ---------- |
| **① 노드 이름**   | 이름이 의미 있을 때                                  | 없음       |
| **② 재질 이름**   | 노드 이름이 무의미해도 재질명은 살아있는 경우가 많음 | 없음       |
| **③ 형상 지문**   | 이름이 전부 무의미할 때                              | 클릭 몇 번 |
| **④ 런타임 배치** | 맵을 전혀 분석하지 않음                              | 0분        |

**②는 의외로 자주 통한다.** 노드가 `Cube.001`이어도 재질은 `Dumpster`, `Fountain`처럼 남아 있는 경우가 많다. 이름 방식이 막히면 재질부터 확인할 것.

**③ 형상 지문**: 같은 종류의 오브젝트는 정점 수·삼각형 수·크기가 정확히 일치한다. 이 값을 지문 삼아 묶으면 이름 없이도 동일 오브젝트가 전부 모인다. 실측상 **97~99%가 자동 그룹화**되며, 1,300개 오브젝트가 수십 개 그룹으로 압축된다.

→ 개발용 화면에서 오브젝트를 클릭하면 같은 지문 전체가 한 번에 태깅되게 하면, 맵당 클릭 몇 번으로 끝난다. **이 그룹화는 인스턴싱 최적화에도 그대로 재활용**되므로 어차피 만들어두면 이득이다.

**④ 런타임 배치**: 바닥에 아래로 레이캐스트를 쏴서 평평한 지점(법선 y > 0.9)에만 자체 오브젝트를 놓는다. 준비 0분이지만 배경과 겉돌 수 있고, 맵마다 인상이 비슷해진다.

### 4-2. 게임 요소 ↔ 앵커 역할 대응

**역할 이름을 모든 맵에서 동일하게 유지**하면 로직을 그대로 재사용할 수 있다.

| 역할       | 어떤 오브젝트를 찾을까                              |
| ---------- | --------------------------------------------------- |
| `spawn`    | 캠프·모닥불·텐트·벤치 등 안전해 보이는 지점         |
| `portal`   | **원형·관문 형태** — 마법진, 아치, 분수, 문틀, 터널 |
| `exit`     | 맵 외곽의 문·다리·길 끝. 없으면 수동 좌표           |
| `lootRoom` | 실내 공간 — 건물, 신전, 광산, 상점, 창고            |
| `lootBox`  | 상자·통·가방·작업대·쓰레기통                        |
| `cover`    | 바리케이드·울타리·바위·벽                           |
| `light`    | 가로등·랜턴·횃불 (경로 유도에도 활용)               |

**포탈은 이미 포탈처럼 생긴 것을 찾는 게 핵심이다.** 마법진이나 아치는 이펙트만 얹으면 되므로 별도 모델이 필요 없다.

### 4-3. 처리 규칙

- 앵커로 쓴 원본 오브젝트는 보통 `visible = false`로 숨기고 자체 오브젝트를 놓는다.
- **시각적으로 이미 어울리는 것(마법진·아치·분수 등)은 그대로 두고 이펙트만 얹는다.**
- 앵커가 없는 역할은 `manualPoints`에 좌표를 직접 적는다. `exit`가 특히 자주 비어 있다.
- 좌표는 정규화 이후 기준으로 JSON에 저장해 두고, 코드는 그 JSON만 읽게 한다.

## 5. 최적화

맵 출처가 달라도 문제 양상은 대체로 같으므로, **동일한 파이프라인을 전 맵에 그대로 적용**하면 된다.

| 작업                      | 효과                                                                                          |
| ------------------------- | --------------------------------------------------------------------------------------------- |
| 불필요한 UV2 제거         | 라이트맵용 UV. 웹게임에선 순수 낭비                                                           |
| 중복 형상 병합 + 인스턴싱 | Sketchfab 파일은 **메시 재사용이 0건**인 경우가 대부분. 같은 나무 100그루가 100번 복사 저장됨 |
| Draco 압축                | 형상 데이터 80~90% 절감                                                                       |
| 텍스처 KTX2 변환          | VRAM 1/4~1/6로 절감                                                                           |

`gltf-transform` 등으로 전 맵에 같은 명령을 돌린다.

### 용량에 대한 감각

- **파일 크기 ≠ 전송량.** 서버 압축(gzip/brotli)을 켜면 형상 데이터는 80% 가까이 줄어든다. 34MB 파일이 실제로는 7MB 정도로 전송된다. 대부분의 호스팅에서 기본 활성화되어 있다.
- **파일 크기 ≠ VRAM.** 텍스처는 파일에서 작아도 GPU 메모리에서는 크게 부푼다. 2048×2048 4장이면 약 69MB. 저사양 기기에서는 이쪽이 더 큰 병목이다.
- glTF와 GLB는 같은 데이터이며 포장만 다르다. **웹 로드용 최종본은 GLB**, 텍스처를 자주 교체하는 작업 단계에서는 분리형 glTF가 편하다.

## 6. 맵 추가 절차

새 맵을 들일 때 아래 순서로 확인한다.

1. **속성 파악** — 크기, unlit 여부, 알파, 텍스처 수, 애니메이션·뼈대, UV2 (3장 표)
2. **최적화 파이프라인 통과** (5장)
3. **설정 항목 작성** — url, targetSize, 조명 프리셋
4. **정규화 검증** — 기존 맵과 같은 속도로 움직이는지 확인. **이게 맞아야 이후가 편하다.**
5. **앵커 탐색** — 노드 이름 → 재질 이름 → 형상 지문 순으로 시도
6. **역할 대응표 채우기** (4-2). 빈 역할은 수동 좌표로
7. 조명 프리셋 미세 조정

## 7. 라이선스 체크

맵을 새로 들일 때마다 확인한다. **공개 배포 전에는 반드시 정리할 것.**

| 상태                                 | 대응                                         |
| ------------------------------------ | -------------------------------------------- |
| 라이선스 파일 있음 + 작가 명시       | 크레딧 표기하고 사용                         |
| 라이선스 파일 없음 (맨 GLB)          | 원본 페이지 표기 확인                        |
| 파일 내부에 상용 팩·게임사 명명 규칙 | 뜯어온 에셋일 가능성 높음. 배포용으로 부적합 |

**주의**: 업로드 페이지에 CC 라이선스가 붙어 있어도, 업로더가 저작권자가 아니면 효력이 없다. 재질·오브젝트 이름에 상용 팩 이름이나 특정 게임사의 명명 규칙이 그대로 남아 있으면 뜯어온 에셋으로 보는 편이 안전하다.

개인 연습·프로토타입 단계에서는 실질적 위험이 낮지만, 공개·수익화 시점에는 정품 구매나 CC0 에셋으로 교체하는 것을 전제로 진행할 것. 형식이 같으므로 교체 자체는 어렵지 않다.
